# 核心规则

## 适用范围

新增、修改、重构、调试、测试、审查代码，以及变更数据库、契约、依赖、配置或实现计划时，必须遵循本规范。

纯产品讨论、UI视觉探索、文案修改和只读查询不强制加载编码规则。UI进入组件实现后必须加载。

## 规则等级

- `FORBIDDEN`：绝对禁止；违反时停止实现或合并。
- `REQUIRED`：必须做到；具体实现选择最简单的正确方式。
- `RECOMMENDED`：默认遵循；偏离时说明理由。

只有AI容易反复犯、可能静默失败或造成严重损失、且自动工具无法充分拦截的规则，才升级为 `FORBIDDEN`。

## 优先级

1. 用户当前任务的明确要求。
2. 已批准的架构设计和架构决策。
3. 本规范。
4. 已确认的接口契约与测试。
5. 既有代码习惯。

遇到架构、安全或数据冲突时，指出冲突、影响和最小修改方案，等待确认。不得静默绕过，不得擅自修改架构。

既有代码违反规范时，不继续复制错误；只修复当前任务涉及范围，不顺手重构整个项目。

## 最小正确实现

代码审查先检查无用代码和过度设计。

- 用满足当前需求、安全和测试的最少代码实现功能。
- 能用简单函数解决时，不创建类、工厂、策略或插件系统。
- 只有一种实现时，不提前建立多层接口；数据库、支付、文件存储等真实外部边界除外。
- 不创建只有转发作用的空壳文件和层。
- 相同校验规则只定义一次。
- 数据在可信边界验证后，内部不层层重复验证。
- 纯本地数据不上传服务器只为重复验证。
- 不为尚不存在的第二种实现建设通用框架。
- 两三行简单重复代码不急于抽象；出现真实稳定重复后再提取。
- 新增接口、适配器、封装层或通用组件时，说明它当前解决的问题。
- 删除不影响当前功能、测试、安全或维护性的代码。

“最少”指最少正确代码。支付、鉴权、学习包使用权和外部输入不得因减少代码而省略服务端校验。

## AI任务流程

1. 读取架构、相关规则、当前模块和相关测试。
2. 用一句话重述目标并列出验收条件。
3. 明确允许修改的目录和预计文件。
4. 检查现有实现，避免重复模块。
5. 对业务逻辑或缺陷先写失败测试。
6. 实现最小范围修改。
7. 运行格式化、类型检查、相关测试和构建。
8. 检查最终差异，排除无关修改。
9. 汇报改动、验证结果、残余风险和未执行项。

一个任务只解决一个明确行为或紧密相关垂直功能。禁止无关重构、占位函数、假数据、空页面和虚假完成声明。

只有文件互不重叠且接口冻结的任务可并行。数据库Schema、共享契约、根配置和锁文件必须串行修改。多个AI不得同时编辑同一文件。

## 依赖

- 统一使用pnpm，只保留 `pnpm-lock.yaml`。
- `FORBIDDEN`：`npm install`、Yarn、新增 `require()`、手工修改锁文件。
- 使用ESM `import/export`。
- 网络使用原生 `fetch`和项目轻量封装，不引入Axios。
- 日期优先使用原生 `Date`、`Intl`和少量项目函数；复杂需求经批准后使用 `date-fns`。
- 禁止Moment.js、jQuery、整包Lodash和功能重复依赖。
- 依赖安装到实际使用的workspace，不堆在Monorepo根目录。
- 批准计划内依赖可直接安装；计划外运行时依赖先说明用途、替代方案、维护状态和移动端体积影响。
- 计划外开发依赖可以添加，但交付时必须列明。

## 环境配置

- `.env`、证书和密钥不得提交；仓库只保存无真实值的 `.env.example`。
- 环境变量通过单一配置模块读取和校验。
- 缺少必要配置时启动失败，不使用不安全默认值。
- 进入移动端构建的变量均视为公开信息。

## Git

- 修改前后检查工作区状态。
- 用户已有修改不得擅自回退、格式化或纳入任务。
- 一个提交只有一个目的。
- 提交格式为英文类型加中文说明，例如 `fix(api): 防止重复发放学习包权限`。
- 类型限定为 `feat`、`fix`、`test`、`refactor`、`docs`、`chore`。
- 只有用户明确要求或批准计划要求时，AI才能提交。
- 按明确路径暂存文件。
- 禁止重写历史、强制推送和破坏性还原。
- 禁止提交密钥、备份、构建产物和缓存。
- 迁移、契约变化和对应测试在同一功能提交中保持可运行。
